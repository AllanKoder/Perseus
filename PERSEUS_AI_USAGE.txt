Perseus — AI / LLM Integration Guide, CLI Usage, and Configuration Specification

Overview
--------
Perseus is a lightweight documentation extractor and static site builder that
scans source trees for embedded `@pdoc ... @endp` YAML blocks inside comments,
parses them into structured `PdocBlock` objects, and renders documentation using
Jinja2 templates. This guide explains how AI systems (LLMs) can interact with
Perseus, how to use the CLI, and the configuration schema and conventions.

1) How LLMs and AI can use Perseus (high-level patterns)
--------------------------------------------------------
- Repository analysis: Use Perseus to extract structured documentation blocks
  from a codebase so LLMs receive concise, validated YAML entries (id/title/
  description/code/etc.) rather than raw noisy comments.
- Incremental prompting: Run Perseus to produce a normalized set of PdocBlocks
  and feed these as context for an LLM prompt. Because blocks are structured,
  an LLM can accurately reference ids, titles, and short descriptions.
- Augmentation loop: Have the LLM suggest improvements for block descriptions,
  tags or vocabulary. Write suggested YAML back to source (as a new @pdoc block
  or edited block) and re-run Perseus to validate and re-render docs.
- Enrichment: Use Perseus' `JiraService` or other enrichment hooks to attach
  runtime metadata (ticket data, external links) to blocks before rendering.
- Template-driven generation: Provide a `.pdoc` Jinja2 template and let the
  LLM generate content for fields (e.g., examples, explanation paragraphs) in
  a format that the template will render directly.

2) Programmatic usage (API)
----------------------------
- Common programmatic entry points in the codebase:
  - `ConfigService().config` — returns a `ConfigData` Pydantic model.
  - `PerseusService(config)` — main orchestrator. Call `PerseusService(cfg).build()`
    to scan and render docs programmatically.
  - `scanner.scan_file(path)` — returns raw `@pdoc` block strings found in a file.
  - `parser.parse_blocks(yaml_blocks, code_text=None)` — parse YAML block strings
    into `PdocBlock` objects.
  - `builder.build_docs(context, out_dir, template_dir, template_file, fmt, template_content)`
    — render docs. If you have a template string in memory (e.g., generated by
    an LLM), pass it via `template_content` to render without writing a template file.

3) CLI usage
------------
Perseus provides a thin Click-based CLI (exposed by `perseus/cli/perseus_cli.py`)
with a `build` command. Example usage from the `perseus` folder:

  uv run main.py --root <project_root> --config perseus.yaml build

CLI options (available via the `build` Click command):
- `--projects` : comma-separated list of project directories to scan (relative to root).
- `--output`   : output directory for generated docs (overrides config `output`).
- `--format` or `-f` : output format, supported: `md` or `json`.
- `--ext`      : comma-separated source extensions to scan, e.g. `.py,.cpp`.
- `--pdoc-ext` : extension for template files (default `.pdoc`).
- `--watch`    : enable watch mode (flag; note: may be a placeholder in demo).

The CLI will echo the built output paths when complete.

4) Config specification (`ConfigData`)
-------------------------------------
Perseus uses a Pydantic model `ConfigData` to represent project configuration.
Fields (defaults shown):

- `root: str` — Project root (default: `.`). Used as base for resolving relative paths.
- `config: str` — Config filename (default: `perseus.yaml`).
- `output: str` — Output root directory (default: `docs/build`). May be relative to `root`.
- `format: str` — Output format (`md` or `json`). Default `md`.
- `source_exts: List[str]` — File extensions to scan. Default `['.py']`. Add
  `.cpp`, `.c`, `.h`, etc. to scan C/C++.
- `pdoc_ext: str` — Template extension (default: `.pdoc`).
- `watch: bool` — Watch mode.
- `ignore_dirs: List[str]` — Directory names (or top-level relative paths) to ignore.
- `projects: List[str]` — Project directories to scan (relative to `root`).
- `jira_base_url`, `jira_email`, `jira_api_token` — Optional Jira enrichment fields.

Notes about path behavior:
- Perseus resolves project directories, template directory/file paths,
  and the output directory to absolute paths using the configured `root`.
- Template outputs are namespaced under the configured `output` directory
  using the template's path relative to its owning project root. You can
  configure output layout via the `output_subdir_for_template()` behavior.

5) Pdoc block format
--------------------
Embed YAML inside comment blocks using `@pdoc` and `@endp` markers. Example
for C/C++ block comments (leading `*` lines are supported):

  /*
   * @pdoc
   * id: my_block
   * title: Example
   * description: |
   *   Multi-line description
   * code: true
   * @endp
   */

Common YAML fields recognized by `PdocBlock` (and types):
- `id: str` (required) — Unique identifier for the block.
- `title: str` — Human-friendly title.
- `description: str` — Markdown or plain text; pipes and block scalars supported.
- `code: bool` — Whether to attempt code-snippet extraction.
- `vocabulary: dict` — Key/value glossary additions.
- `tags: list[str]` — Tags for grouping/filtering.
- `tickets: list` — Ticket identifiers or mappings; normalized at parse time.

6) Comment-style handling and language helper
--------------------------------------------
- Perseus includes a language helper (`perseus.helpers.language`) that maps
  file extensions to comment styles and strips comment prefixes from extracted
  `@pdoc` blocks (e.g., removing leading `*` in `/* ... */` blocks).
- Supported styles are exposed as an Enum `Style` (e.g., `Style.C_LIKE`,
  `Style.PYTHON`) and the helper provides `detect_style_from_path()` and
  `strip_comment_prefixes()`.

7) Code-snippet extraction
--------------------------
- By default `extract_code_near(block_id, source_text)` performs simple
  pattern matching suitable for Python (`def`/`class`) to find and return a
  nearby snippet. For other languages (C/C++, Java, Go, etc.) you should
  extend `extract_code_near` with language-specific regexes (e.g., match
  function signatures like `type name(` or `return_type name(`) and use the
  language helper to select the appropriate pattern.

8) Templates
------------
- Templates are Jinja2 `.pdoc` files. A template receives two variables:
  - `blocks`: mapping of `id` → `PdocBlock` objects
  - `glossary`: mapping used for vocabulary/glossary entries
- Builder API: `builder.build_docs(..., template_content=...)` accepts a
  template string (useful when generating templates in-memory via an LLM).

9) Best practices for LLM workflows
----------------------------------
- Extract first: run Perseus and use parsed blocks as canonical machine-readable
  context for prompts. This reduces ambiguity compared to raw comments.
- Validate suggestions: ask the LLM to output YAML that conforms to the
  `PdocBlock` schema, then run the parser to validate. Reject or flag
  outputs that fail schema validation.
- Use templates for final rendering: have the LLM produce content for fields,
  and let the template render polished Markdown/JSON. For programmatic
  templating, provide `template_content` to `builder.build_docs`.
- Incremental commits: if you plan to write generated YAML back to source,
  create a separate review branch and run Perseus on the modified tree to
  validate the results before merging.

10) Quick examples
------------------
- Build from CLI (from `perseus` folder):

  pushd /path/to/Perseus/perseus
  uv run main.py --root /path/to/project --config perseus.yaml build

- Programmatic (Python):

  from perseus.services.config_service import ConfigService
  from perseus.services.perseus_service import PerseusService

  cfg = ConfigService().config
  # override programmatically
  cfg.source_exts = ['.cpp', '.c', '.h']
  svc = PerseusService(cfg)
  outpaths = svc.build()

- Render a template string in-memory (LLM-generated template):

  from perseus.core import builder
  builder.build_docs(context, out_dir, template_dir=None, template_file=None, template_content=llm_generated_template)

11) Extending Perseus
---------------------
- Add language-specific code-extraction patterns in `perseus/core/parser.py` or
  a dedicated module; use `helpers.language.detect_style_from_path()` to pick
  the right pattern.
- Add new file-extension mappings in `perseus/helpers/language.py` (or add
  content-based heuristics).
- Add enrichment hooks (e.g., backends for GitHub issues, Confluence) similar
  to `JiraService`.

12) Troubleshooting
-------------------
- Empty template output: check whether Perseus found any `@pdoc` blocks —
  `PerseusService` logs scanned directories and templates. Ensure `source_exts`
  includes the extension you want to scan.
- Template path namespacing: Perseus places template outputs under the
  configured `output` directory using the template's relative path; change
  `ConfigData.output_subdir_for_template()` to alter this behavior.
- Parsing YAML failures: `parser.parse_blocks` falls back to stripping
  known comment prefixes and re-parsing. If your language uses an unusual
  comment format, add a rule into `helpers.language.strip_comment_prefixes`.
